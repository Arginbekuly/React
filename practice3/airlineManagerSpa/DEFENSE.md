# SkyLine Air — памятка для защиты

## Демонстрация на 5–7 минут

1. Открыть приложение: показать 120 моделей, цены и разные фотографии.
2. Найти «Сокол», сбросить поиск, отсортировать по доходности и переключить страницу.
3. Открыть детали: показать loading, паспорт, цены и похожие модели. Обновить страницу — hash-ссылка сохраняет выбранный экран.
4. Купить борт, открыть «Мой парк», ввести заметку. Купить второй борт и изменить порядок: заметка остаётся у своего самолёта.
5. Нажать «Сбросить карточку»: сбросятся заметка и направление только этой карточки.
6. Назначить маршрут, открыть «Рейсы» и завершить рейс. Показать начисление дохода и рост износа. При необходимости отправить борт на ТО и завершить обслуживание.
7. В конструкторе проверить невалидное имя, затем создать модель. Во время отправки элементы управления блокируются; после успеха форма сбрасывается.
8. Открыть `?demo=1#catalog`: вызвать ошибку каталога и нажать «Повторить». В этом режиме также доступны ошибка деталей и ошибка отправки формы.

Не очищайте основное сохранение ради демонстрации. Для чистого запуска используйте отдельный профиль/приватное окно. Данные localStorage привязаны к браузеру и origin: localhost и публичный сайт имеют разные сохранения.

## Дерево компонентов и поток данных

```text
App
├─ useAirline → fakeApi → JSON/localStorage
├─ Header → StatTicket
├─ Hero → DepartureBoard
├─ Catalog → useDebounce, fakeApi.getAircraft
│  ├─ FilterChips
│  ├─ LoadingState / ErrorMessage / EmptyState
│  ├─ AircraftCard → AircraftStats
│  └─ Pagination
├─ AircraftForm → AircraftPreview
├─ FleetSection → FleetCard → StatusBadge, WearGauge
├─ AircraftPage → fakeApi.getAircraftById → детали / состояния
├─ MaintenancePage → MaintenanceRow, HangarCard
├─ FlightsPage → FlightListItem, RouteMap
├─ ConfirmModal
└─ Toast
```

`App` соединяет компоненты и навигацию. Данные идут вниз через props. Дочерний компонент вызывает переданный обработчик: например, карточка вызывает `onBuy(plane)`, `useAirline` отправляет команду в API, затем обновляет снимок данных. Карточка не меняет баланс напрямую.

## State: где и почему

| Состояние | Место | Причина |
|---|---|---|
| Баланс, парк, ангары, рейсы и журнал | `useAirline` | Нужны разным экранам; хук используется один раз в App. |
| Начальные модели и сохранённые данные | API/localStorage | Единственный источник данных; React хранит полученные снимки, а не независимую базу. |
| Поиск, фильтр, сортировка, страница | `Catalog` | Влияют только на каталог. |
| Ответ каталога и ошибка запроса | `Catalog` | Жизненный цикл конкретного запроса. |
| Поля, sending, ошибка и успех формы | `AircraftForm` | Нужны только форме. |
| Заметка и выбранное направление | `FleetCard` | Независимы для каждого борта. |
| Версия key для сброса | `FleetSection` | Родитель управляет идентичностью карточки. |
| Выбранный рейс и фильтр | `FlightsPage` | Локальное управление табло. |
| Экран, ID деталей, подтверждение | `App` | Управляют композицией приложения. |

## Controlled inputs и события

Контролируемое поле получает `value` из state, а `onChange` обновляет этот state. Источник значения — React. `onSubmit` отменяет стандартную перезагрузку страницы и отправляет данные в API. Формула цены повторно вычисляется в API, чтобы не доверять произвольной цене из формы.

События покупки, аренды, запуска рейса, ТО и продажи изменяют данные через API. Изменение фильтра или заметки — локальное событие и не требует записи в API.

## Как API-данные попадают на экран

1. Эффект каталога создаёт `AbortController`.
2. `fakeApi.getAircraft` возвращает Promise с задержкой 300–600 мс.
3. После задержки API читает JSON из localStorage, выполняет поиск/фильтрацию/сортировку/пагинацию.
4. Компонент получает `{ items, total, counts, page, perPage }` и сохраняет ответ в state.
5. React вызывает render; карточки получают элементы через props.

Все бизнес-операции тоже асинхронные. Внутри операции API повторно читает актуальное сохранение и проверяет ограничения. Успех показывается только после успешной записи в localStorage.

## useEffect и зависимости

- `useAirline`: эффект начальной загрузки зависит от `retryKey`. Очистка отменяет загрузку и незавершённую команду при размонтировании.
- `Catalog`: эффект зависит от `requestKey` — JSON-строки всех параметров запроса: поиска после debounce, фильтра, сортировки, страницы, размера страницы, ревизии данных, retry и тестовой ошибки. Изменение любого параметра создаёт новый ключ и новый запрос.
- `AircraftPage`: ключ запроса содержит ID, ревизию, retry и тестовую ошибку.
- `useDebounce`: зависимости `[value, delay]`; cleanup очищает прежний таймер.
- `Toast`: зависимости `[notice, onClose]`; cleanup очищает таймер закрытия.
- `App`: эффект с `[]` подписывается на hashchange и отписывается в cleanup.

Покупку не надо переносить в useEffect: это результат пользовательского события. Эффекты нужны для синхронизации с источником данных, URL или таймером, а не для каждого вычисления.

## Cleanup, stale closures и race conditions

Эффект захватывает значения своего render — это closure. Если пользователь быстро сменил поиск, старый ответ может прийти позже нового. Без защиты он подменит актуальные данные.

В cleanup вызывается `controller.abort()`. API очищает таймер и отклоняет Promise с `AbortError`; компонент игнорирует отменённую операцию. Дополнительная проверка `signal.aborted` перед обновлением state защищает момент между завершением Promise и обработчиком результата.

Команда покупки не вычисляет новый баланс по старому `game` из closure. API читает актуальное сохранение непосредственно перед изменением. Повторное завершение одного рейса не начисляет доход второй раз. Эти случаи покрыты тестами.

## Loading, error, empty, success

| Состояние | Пример |
|---|---|
| Loading | Открытие кассы, смена параметров каталога, загрузка деталей; у формы — `Сохраняем модель…`. |
| Error | Ошибка API с «Повторить», ошибка отправки формы с сохранёнными полями, бизнес-ошибка покупки. |
| Empty | Ничего не найдено, пустой парк/табло, отсутствующий ID модели. |
| Success | Загруженные карточки, сообщение о создании, Toast и журнал операции. |

Ошибка в режиме `?demo=1` управляемая. В обычном режиме случайных сбоев нет: это сохраняет предсказуемость демонстрации.

## Rerender, snapshots и batching

`setState` планирует новый render. Текущий обработчик продолжает видеть снимок state того render, в котором он был создан. React группирует несколько обновлений, когда это возможно.

Например, несколько вызовов `setCount(count + 1)` в одном обработчике используют одно и то же значение `count`. Чтобы несколько раз прибавить к последнему значению, нужны функциональные обновления: `setCount(previous => previous + 1)`.

В проекте `setRetryKey(value => value + 1)` использует предыдущее значение. Для защиты от второго клика до следующего render `useAirline` хранит текущую команду в ref: изменение ref происходит сразу и не требует render.

Изменение заметки перерисовывает `FleetCard`. Изменение данных авиакомпании перерисовывает App и его дочерние компоненты. Вызов render не означает, что React заново создаёт весь DOM.

## Render vs commit

Render вычисляет новое дерево элементов из props/state и должен быть чистым. Commit применяет необходимые изменения к DOM. Эффекты запускаются после commit; cleanup прежнего эффекта выполняется перед следующим запуском или при размонтировании.

StrictMode в разработке помогает выявлять нечистый render и ошибки cleanup. Повторная проверка эффекта не должна приводить к двум покупкам: покупки запускаются обработчиками, а отменённая загрузка не изменяет данные.

## Reconciliation, keys и identity

React сопоставляет элементы по типу, позиции и key. Для моделей и бортов используется стабильный ID, а не индекс текущего списка. Перестановка карточек не переносит заметку на другой борт.

Ключ парка: `${plane.id}-${resetVersion}`. Изменение версии заставляет React размонтировать старую карточку и создать новую — её локальные поля сбрасываются. Кнопка поэтому называется «Сбросить карточку».

При фильтрации исключённая карточка размонтируется и теряет локальные поля. При возвращении она создаётся снова. Это осознанное поведение, отличающееся от сохранения при reorder. Главная при переключении экрана скрывается, поэтому каталог и форма остаются смонтированными. Детали получают `key={id}` и сбрасывают локальные поля при смене модели.

## Иммутабельность

Обновление записи создаёт новый объект через spread. Обновление массива — через `map`, `filter`, spread. Сортировка применяется к новому массиву, полученному через `filter`. API возвращает JSON-копии: изменение ответа снаружи не меняет сохранение.

## Навигация и деплой

Навигация использует hash: `#catalog`, `#aircraft/1`, `#maintenance`, `#flights`. Браузерная история и обновление деталей работают без серверных rewrite-правил. React Router не является требованием PDF.

Simulated API работает в браузере; отдельный сервер не нужен. Это не общий серверный аккаунт: данные не синхронизируются между устройствами и браузерами. При первой загрузке на новом origin создаётся исходный набор.

## Восемь тренировочных изменений

1. **Фильтр:** добавить ограничение «больше 200 мест» в запрос и реализовать его в `fakeApi.getAircraft`; сбрасывать страницу при смене.
2. **Controlled input:** добавить поле заметки в форму через `value` и `onChange`; не читать значение через DOM.
3. **API-поле:** добавить характеристику в seed и ответ, затем вывести через `AircraftStats`.
4. **Reset:** добавить кнопку сброса фильтров либо объяснить существующий сброс key карточки.
5. **Зависимость effect:** убрать параметр из requestKey на локальном примере и объяснить, почему ответ перестанет обновляться; вернуть корректную зависимость.
6. **Сортировка:** добавить сортировку по аренде в select и в API, не дублировать её в компоненте.
7. **Loading/error:** открыть `?demo=1`, вызвать ошибку, объяснить loading и retry, затем восстановить запрос.
8. **Событие:** изменить обработчик операции и соответствующий тест, например сумму продажи с 70 % на 65 %.

Для подготовки объясните эти примеры своими словами и выполните изменения самостоятельно. Документ не заменяет практику защиты.
